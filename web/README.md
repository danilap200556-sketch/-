# Сайт склада

Веб-версия приложения для компьютера. **Работает с той же базой PostgreSQL в Яндекс Облаке**, поэтому логины,
товары, склады, остатки и штрихкоды общие: что изменили в приложении - видно на сайте, и наоборот.
Отдельных данных и синхронизации нет, обе программы просто читают и пишут одни и те же таблицы.

## Что есть на сайте

- Вход по логину и паролю из приложения. Смена своего пароля (он меняется и в приложении).
- **Остатки**: поиск по артикулу, названию или штрихкоду (в том числе сканером), фильтр по складу, выгрузка в CSV для Excel.
- **Операции**: приход, списание, перемещение между складами, инвентаризация. Товар можно указать артикулом или штрихкодом.
- **Товары**: добавление, правка, цена, артикул на Маркете, штрихкоды (свои и с коробок, проверка контрольной цифры), место хранения.
- **Склады** и места хранения, **журнал движений**.
- **Пользователи** (только администратор): создать, сбросить пароль, дать/снять права админа, удалить.

Чего на сайте нет (остаётся в приложении): Яндекс Маркет (кабинеты, сверка остатков и цен, заказы, ярлыки),
импорт из Excel, печать этикеток, фотографии товаров (в базе хранится путь к файлу на конкретном компьютере).

Отличия от приложения: пароли на сайте - от 8 символов (в приложении от 4); удалять товары и склады может
только администратор.

## Развёртывание в Яндекс Облаке

Нужны: виртуальная машина (Compute Cloud), домен, уже работающая база с приложением.

### 1. Пользователь базы для сайта

Сайту не нужен доступ к API-ключам Маркета, поэтому дайте ему отдельного пользователя с урезанными правами.

1. Консоль -> Managed Service for PostgreSQL -> ваш кластер -> **Пользователи** -> создать `web_user` с паролем.
   Выдайте ему доступ к вашей базе (роль `mdb_...` не нужна).
2. Откройте файл `grants.sql` (лежит рядом с этим файлом) и выполните его в базе **под владельцем** (тем
   пользователем, под которым работает приложение), например через SQL-консоль в Яндекс Облаке.

Если что-то не получается, можно временно использовать того же пользователя, что и в приложении, но тогда
взлом сайта открывает и ключи Маркета.

> Перед первым запуском сайта хотя бы один раз запустите **свежую версию приложения** с этой базой:
> таблицы создаёт и обновляет оно. Если их нет, сайт отвечает «Сервис временно недоступен» (причина - в логах).

### 2. Виртуальная машина

1. Compute Cloud -> создать ВМ: Ubuntu 22.04 или 24.04, 2 vCPU (можно 20% гарантированной доли) и 1-2 ГБ памяти,
   публичный IP.
2. Группа безопасности ВМ: входящие **22** (SSH), **80** и **443** (сайт). Наружу порт базы открывать не нужно.
3. Если ВМ в той же сети (VPC), что и кластер, сайт сможет ходить в базу по внутреннему адресу.
   Если нет - работает и по внешнему, раз у вас включён публичный доступ к кластеру.
4. Зайдите по SSH и поставьте Docker: `curl -fsSL https://get.docker.com | sudo sh`

### 3. Домен

Создайте у регистратора (или в Yandex Cloud DNS) запись **A**: `sklad.ваш-домен.ru` -> публичный IP ВМ.
Без домена HTTPS не получить, а без HTTPS пароли идут открытым текстом, поэтому домен нужен.

### 4. Запуск

```bash
git clone https://github.com/danilap200556-sketch/-.git склад && cd склад/web
mkdir certs && wget -O certs/root.crt https://storage.yandexcloud.net/cloud-certs/CA.pem   # сертификат Яндекса
cp .env.example .env && nano .env      # домен, секрет (openssl rand -hex 32), данные базы
sudo docker compose up -d --build
sudo docker compose logs -f web        # должна быть строка «Сайт склада запущен»
```

Если репозиторий закрытый, `git clone` попросит логин и токен GitHub (Settings -> Developer settings -> Personal
access tokens), либо скопируйте папку `web` на ВМ через `scp`.

Адрес базы в `.env` - **основной хост** кластера вида `c-<id>.rw.mdb.yandexcloud.net` (его даёт кнопка «Подключиться»
в консоли), порт `6432`. Хост-реплика даёт ошибку «read-only transaction».

Откройте `https://sklad.ваш-домен.ru` и войдите логином и паролем из приложения.

### Обновление и обслуживание

```bash
cd ~/склад && git pull && cd web && sudo docker compose up -d --build   # обновить сайт
sudo docker compose logs --tail 100 web                                   # логи
sudo docker compose restart web                                           # перезапуск
```

Сайт сам запускается после перезагрузки ВМ (`restart: unless-stopped`).

## Безопасность (что сделано)

- Пароли хранятся так же, как в приложении (SHA-256 с солью), поэтому подходят в обе стороны. Подбор паролей ограничен:
  5 неудачных попыток для логина с одного IP, затем блокировка на 15 минут.
- Вход держится в подписанном cookie (`HttpOnly`, `Secure`, `SameSite=Lax`, префикс `__Host-`); после смены пароля все
  старые входы закрываются, удалённый пользователь теряет доступ сразу.
- Все формы защищены от подделки запросов (токен + проверка источника), страницы закрыты строгой политикой CSP,
  весь вывод экранируется, все запросы к базе - с параметрами.
- Списание проверяет остаток прямо в запросе: два одновременных списания (с сайта и из приложения) не уведут остаток в минус.
- Рекомендации: отдельный пользователь БД для сайта (шаг 1), `DB_SSL=verify` с сертификатом Яндекса, сильные пароли,
  обновлять ВМ (`sudo apt update && sudo apt upgrade`).

## Разработка и тесты

```bash
cd web && npm ci
# нужен PostgreSQL; параметры по умолчанию - см. test/helpers.js (TEST_DB_HOST, TEST_DB_PASSWORD, ...)
npm test                         # 32 теста на реальной БД
WEB_TEST_RESTRICTED=1 npm test   # то же под пользователем с правами из grants.sql
```

Схема для тестов (`test/schema.sql`) - копия `schemaDdl()` из `src/database.cpp`; обновляется командой
`python3 web/test/extract-schema.py` (CI проверяет, что она не разошлась с приложением).
Запуск без Docker: переменные из `.env.example` + `node server.js` (для проверки без HTTPS: `COOKIE_SECURE=false`).
